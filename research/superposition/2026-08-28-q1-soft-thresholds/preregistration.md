# Q1: предрегистрация — пороги мягкого слоя

Дата: 2026-08-28. Статус: записано ДО новых замеров (фаза 2 протокола
суперпозиции). Реестр гипотез — `registry.md` (тот же каталог).

## Вопрос

Действие мягкого слоя дерева решений (`features_total >= 3` и
`categories_total >= 2`) не наступает ни разу на корпусе (TP=0). Какая
конфигурация действия (если какая-то) должна занять место текущей: статус-кво,
порог T=2/K=1, критичность-управляемое действие или удаление ветки?

## Приорное знание (задекларировано до правила коллапса)

Все числа этого раздела уже собраны и опубликованы (F5, 2026-08-14,
`research/soft-threshold-sweep/`); они — контекст вопроса, не новый замер:

- Максимум признаков: ИИ 2, человек 0 (per-file) / 1 (neutral), boundary 0.
- Сетка per-file: T=1/K=1 → TP=15, FP=0; T=1/K=2 → TP=5, FP=0; T=2/K=1 →
  TP=7, FP=0; T=2/K=2 → TP=5, FP=0; T≥3 → TP=0.
- Сетка neutral: T=1/K=1 → TP=15, **FP=4**; T=2/K=1 и T=2/K=2 → TP=7/5,
  FP=0; остальное — нули.
- K-аблация (из сетки): при T=2 понижение K с 2 до 1 поднимает recall
  (5→7) и не поднимает FP (0→0 в обоих режимах). K на этом корпусе не
  несёт FP-защиты.
- Частичный peek: при проверке формата JSON просмотрены findings трёх
  ИИ-файлов (alisa/01, copilot/01, copilot/02) — во всех трёх сработал
  детектор критичности «высокая». Это влияет на прогноз H-C (указан ниже).

## Что измеряется в этом цикле (новое)

Один замерный прогон `measure.py` (замораживается хешем вместе с корпусами)
по замороженному корпусу; режимы per-file (жанровые решения
threshold_sweep.py) и neutral:

1. **Пересчёт сетки** (целостность приорных чисел: свежие прогоны сканера
   обязаны воспроизвести perfile.json/neutral.json пофайлово — H-S6).
2. **Агрегат критичности**: TP_HC/FP_HC/boundary_HC для max-gate «≥1 признак
   crit=высокая» в обоих режимах (H-C).
3. **Гистограмма детекторов**: сколько из 33 сработали на ИИ-корпусе,
   концентрация топ-2, разбивка по категориям (H-S1/H-S2/H-S3).
4. **Агрегация**: сумма сырых `count` против `features_total` на ИИ-корпусе
   (H-S4).
5. **Подпороговые потери**: инструментальный прогон finder'ов в обход
   `min_hits` — детекторы с 1 ≤ hits < min_hits на ИИ-файлах (H-S5).
6. **Преднормализация**: кавычки/тире/NBSP → канон, пересчёт, дельта числа
   срабатываний (H-S7).
7. **Диагностика второго порядка**: AUC разделения 24 ИИ / 26 человек по
   `features_total` и по дисперсии длины предложений (H-D).

## Прогнозы (до прогона)

- P1 (H-S6): пофайловое `features_total` свежего прогона совпадает с
  `perfile.json` и `neutral.json` на всех 52 файлах.
- P2 (H-C): TP_HC ≥ 5/24; FP_HC = 0 и boundary_HC = 0 в обоих режимах.
- P3 (H-S1): сработавших детекторов ≤ 10 из 33.
- P4 (H-S2): топ-2 детектора дают ≥ 80% срабатываний на ИИ-корпусе.
- P5 (H-S3): суммарные срабатывания структурной и коммуникативной категорий
  на ИИ-корпусе > 0 (приор уже опровергал нуль — замер даёт точное число).
- P6 (H-S4): сумма count ≥ 3 × features_total на ИИ-корпусе.
- P7 (H-S5): подпороговые потери существуют (≥ 1 детектор с 1 ≤ hits <
  min_hits хотя бы на одном ИИ-файле).
- P8 (H-S7): преднормализация меняет суммарно < 3 срабатываний.
- P9 (H-D): AUC ритма ≤ AUC счёта (прогноз консервативный: счёт уже
  даёт разделение 24/26 почти идеальное — человеческие в per-file все 0).
- P10 (гонка): H-T (T=2/K=1) даёт recall 7/24; H-C даёт recall ≥ 5/24.

Каждый прогноз имеет фальшификатор в `registry.md`; расхождение прогноза с
замером публикуется как есть и не правится задним числом.

## Правило коллапса (заморожено дословно)

Побеждает гипотеза с максимальным recall (TP/24, режим per-file) среди
прошедших блокирующий гейт: FP=0 на 26 человеческих файлах И ноль
срабатываний на 2 boundary-контролях В ОБОИХ режимах (per-file и neutral).
При равенстве recall побеждает меньшая сложность имплементации — число
затронутых файлов репозитория. Если ни одна гипотеза, кроме H0, не проходит
гейт с recall > 0, конфигурация не коллапсирует: H0 остаётся, вопрос
переносится в суперпозицию до появления данных (дикая выборка, вторая
семья генератора, корпус «правка запрошена»). Гипотезы, требующие данных
вне замороженного корпуса (H-A1…H-A4, H-V, H-P, Σw-калибровка), в гонке не
участвуют и остаются alive с evidence_needed. Итог гонки — конфигурация
действия; рамочные вопросы (назначение слоя H-P, вердикт-утечка H-A4,
валидность корпуса H-V) выносятся владельцу в decision.md независимо.
Решение подписывает владелец (меняет поведение скилла).
