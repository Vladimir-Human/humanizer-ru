## Что такое кэш и зачем нам Redis

Для новичков: **кэш** — это временное хранилище часто используемых данных, чтобы не запрашивать их каждый раз из «дорогих» мест: базы данных, внешних сервисов или из тяжёлых вычислений.

Простыми словами: если ответ на один и тот же вопрос можно получить быстро из памяти, зачем заново считать его с нуля.

---

## Зачем нам Redis

**Redis** — это быстрый кэш/хранилище в памяти. Мы используем его, чтобы хранить готовые ответы API или промежуточные данные на короткое время.

У нас есть измеримый эффект:

- API без кэша: **~800 мс**
- API с Redis: **~40 мс**

То есть кэш делает ответы примерно **в 20 раз быстрее**.

Для пользователя это означает, что интерфейс загружается почти мгновенно. Для системы — меньше нагрузки на базу данных и внешние сервисы.

---

## Как это выглядит в практике

Допустим, пользователь часто запрашивает список товаров, профиль категории или какую-то агрегированную информацию.

Без кэша каждый запрос идёт в базу:

```text
Запрос → проверка прав → запрос к базе → агрегация → ответ
```

С кэшем:

```text
Запрос → есть данные в Redis? → да → ответ
                         → нет → запрос к базе → сохранить в Redis → ответ
```

Когда Redis возвращает данные, мы экономим время на обращении к базе и повторных вычислениях.

---

## Сколько хранится кэш

У нас кэш живёт **10 минут**.

Это значит, что после записи данных в Redis они хранятся там максимум 10 минут, а затем «протухают» и следующий запрос снова пойдёт в источник данных.

Например:

```text
00:00 — данные положили в Redis
00:05 — данные ещё валидны
00:10 — данные истекли, следующий запрос пойдёт в базу
```

Такой TTL, время жизни, выбирают, чтобы найти баланс между скоростью и актуальностью данных.

---

## Почему нельзя кэшировать всё без ограничений

Кэш полезен, но его нужно использовать аккуратно.

Плохая практика:

- кэшировать данные, которые быстро меняются;
- показывать пользователям устаревшую информацию;
- кэшировать персональные данные без понимания, кто и когда их должен видеть;
- кэшировать финансовые и платёжные операции.

Например, если данные изменили в базе, а кэш ещё живёт 10 минут, пользователь может увидеть старую информацию. Поэтому для некоторых данных кэш не подходит или требует аккуратной инвалидации.

---

## Главное исключение: платежи

**Данные о платежах мы никогда не кэшируем.**

Это важное правило. Платёжная информация не должна храниться в кэше, потому что:

- она слишком чувствительная;
- она должна быть актуальной на момент запроса;
- кэш может привести к отображению устаревшего или неверного состояния платежа;
- ошибки в платёжных данных могут быть критичными.

Если у вас код, API, дашборд, аналитика или любой сценарий касается платежей — не используйте Redis для кэширования таких ответов.

Правильное поведение:

```text
Платёжный запрос → всегда идти в источник данных → не сохранять в Redis
```

---

## Как запомнить простую аналогию

Кэш — это как шпаргалка рядом с учителем.

Если ученик часто спрашивает одно и то же, учитель может быстро посмотреть в шпаргалку. Но если вопрос про деньги и платежи — шпаргалку использовать нельзя, нужно проверять по оригиналу.

Или ещё проще:

- обычный API без кэша — каждый раз заново собирать пазл;
- Redis — заранее собранная картинка, которая хранится 10 минут;
- платежи — документы, которые нельзя брать из «картинки на 10 минут», они должны быть точными прямо сейчас.

---

## Что нужно помнить при разработке

1. **Redis ускоряет чтение данных**  
   Он особенно хорош для запросов, которые часто повторяются и не требуют идеальной свежести каждую миллисекунду.

2. **Кэш не является источником истины**  
   Настоящие данные хранятся в базе/сервисе. Redis — только ускоритель.

3. **TTL 10 минут**  
   Данные в кэше могут быть не самыми свежими. Учитывайте это при проектировании UI и бизнес-логики.

4. **Платежи — не кэшируем**  
   Никогда не добавляйте платёжные данные в Redis как кэш. Это запрещённая область.

5. **Если данные критичны к свежести — подумайте дважды**  
   Кэш уместен там, где 10-минутная задержка в обновлении допустима.

---

## Итог

Redis нужен нам, чтобы сделать API быстрым:  
вместо **800 мс** ответ занимает **40 мс**.

Мы кэшируем данные на **10 минут**, но никогда не кэшируем **данные о платежах**.

Простое правило:

```text
Обычные быстрые данные → можно кэшировать
Платежи → никогда не кэшировать
```
