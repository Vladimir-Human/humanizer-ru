# Процесс код-ревью (Code Review)

## Зачем это нужно
Код-ревью — не галочка для галочки. Это способ делиться знаниями, ловить баги до прода и не давать кодовой базе скатываться. Смотрим на ревью как на асинхронное парное программирование: вместе делаем продукт лучше.

---

## Кто смотрит PR

### Два ревьюера
Перед мержем каждый Pull Request должен получить **минимум два апрува**. Одного мало, даже если изменения «простые».

### Ревью из другой команды (обязательно)
**Один из ревьюеров должен быть из другой команды.**

Почему так:
- Внутри команды легко получить «туннельное зрение», а чужой взгляд его ломает
- Проблемы интеграции находятся раньше
- Хорошие практики расходятся между отделами
- Свежий глаз замечает то, к чему свои уже привыкли

> 💡 **Пример:** если вы из Backend, одним из ревьюеров должен быть человек из Frontend, Mobile, Data, DevOps или любой другой команды.

---

## Размер PR: правило 400 строк

Если в вашем PR **больше 400 строк изменений** (автогенерированный код, lock-файлы, миграции БД и конфиги не считаем), **пожалуйста, разбейте его на несколько логичных PR**.

**Почему это важно:**
- Большой PR трудно проверить как следует: после 200–300 строк внимание ревьюера падает
- Шанс пропустить серьёзный баг растёт экспоненциально
- Долгое ревью блокирует коллег и тормозит поставку фич

**Исключения:** срочные хотфиксы в прод и крупный рефакторинг инфраструктуры (по согласованию с техлидом).

> 🛠 **Совет:** если в 400 строк не влезть, вынесите подготовительные изменения (рефакторинг, подготовку тестов) в отдельный PR, а основную логику оставьте для следующего.

---

## Когда можно мержить

### ⛔ Никаких деплоев в пятницу вечером
**Мержить PR в пятницу после 16:00 запрещено** (по местному времени офиса).

**Почему:**
- После выката не хватит времени на мониторинг
- Если что-то сломается, быстро среагировать будет некому
- Выходные не созданы для дежурств по проду

**Как быть:**
- Крупные фичи мержите **до 16:00 в пятницу** или в **понедельник**
- Мелкие багфиксы можно, если вы уверены на 100% и рядом есть кто-то из дежурных

## Чек-лист автора PR

Прежде чем создавать PR, проверьте:
- [ ] В PR меньше 400 строк (или есть задокументированное исключение)
- [ ] В описании понятно, что делает код и **зачем** (со ссылкой на тикет)
- [ ] Для UI-изменений добавлены скриншоты или видео
- [ ] Тесты добавлены или обновлены (или объяснено, почему они не нужны)
- [ ] Запрошены ревьюеры: **минимум 2 человека**, один из другой команды
- [ ] CI зелёный, линтеры прошли
- [ ] Вы сами просмотрели diff перед публикацией

---

## Чек-лист ревьюера

Во время ревью проверьте:
- [ ] Код решает заявленную задачу, а не «просто работает»
- [ ] Нет очевидных багов, утечек памяти, N+1 запросов
- [ ] Соблюдены стандарты кодирования команды
- [ ] Критичная логика покрыта тестами
- [ ] Документация и комментарии обновлены (если менялся API)
- [ ] В коде нет секретов, токенов и персональных данных
- [ ] Изменения не ломают смежные модули (особенно важно при ревью из другой команды)

**SLA:** старайтесь посмотреть PR в течение **одного рабочего дня**. Не успеваете — напишите автору.

---
