# Процесс код-ревью (Code Review)

## Зачем нужно ревью
Код-ревью нужно, чтобы делиться знаниями, ловить баги до прода и держать качество кодовой базы. Относимся к нему как к асинхронному парному программированию.

## Кто смотрит PR

### Правило двух ревьюеров
Каждый Pull Request должен получить минимум два апрува перед мержем. Одного мало, даже если изменения простые.

### Кросс-командное ревью (обязательно)
Один из ревьюеров должен быть из другой команды. Так мы:
- не застреваем в «туннельном зрении» внутри команды;
- раньше находим проблемы интеграции;
- переносим лучшие практики между отделами;
- получаем свежий взгляд на то, к чему «свои» привыкли.

Пример: если вы из команды Backend, один из ревьюеров должен быть из Frontend, Mobile, Data, DevOps или другой команды.

## Размер PR: правило 400 строк

Если в PR больше 400 строк изменений, разбейте его на несколько логических PR. Автогенерированный код, lock-файлы, миграции БД и конфиги не считаются.

Большие PR сложно проверить качественно: после 200–300 строк внимание ревьюера падает. Риск пропустить критичный баг растёт экспоненциально. Долгое ревью блокирует коллег и замедляет доставку фич.

Исключения: срочные хотфиксы в прод и крупный рефакторинг инфраструктуры (по согласованию с техлидом).

Если в 400 строк не укладывается, вынесите подготовительные изменения (рефакторинг, подготовку тестов) в отдельный PR, а основную логику оставьте для следующего.

## Когда можно мержить

### Пятничный деплой запрещён
Мержить PR в пятницу после 16:00 по локальному времени офиса запрещено. После выката не хватит времени на мониторинг, а если что-то сломается, оперативно реагировать будет некому. На выходных по проду никто не должен дежурить.

Что делать:
- Крупные фичи мержите до пятницы 16:00 или в понедельник.
- Мелкие багфиксы можно мержить, если вы уверены на 100% и на связи кто-то из дежурных.

## Чек-лист для автора PR

Перед созданием PR проверьте:
- [ ] В PR меньше 400 строк (или есть задокументированное исключение).
- [ ] В описании понятно, что делает код и зачем (со ссылкой на тикет).
- [ ] Для UI-изменений добавлены скриншоты или видео.
- [ ] Тесты добавлены или обновлены (или объяснено, почему они не нужны).
- [ ] Запрошены минимум 2 ревьюера, один из другой команды.
- [ ] CI зелёный, линтеры прошли.
- [ ] Вы сами посмотрели diff перед публикацией.

## Чек-лист для ревьюера

При ревью проверьте:
- [ ] Код решает заявленную задачу, а не просто работает.
- [ ] Нет очевидных багов, утечек памяти, N+1 запросов.
- [ ] Соблюдены стандарты кодирования команды.
- [ ] Критичная логика покрыта тестами.
- [ ] Документация и комментарии обновлены (если менялся API).
- [ ] В коде нет секретов, токенов и персональных данных.
- [ ] Изменения не ломают смежные модули (особенно важно для кросс-командного ревью).

SLA: постарайтесь посмотреть PR в течение одного рабочего дня. Если не успеваете, напишите автору.

## Процесс по шагам

1. Автор создаёт PR и назначает ревьюеров (минимум 2, один из другой команды).
2. Ревьюеры оставляют комментарии и выставляют `Approve` или `Request changes`.
3. Автор исправляет замечания и отвечает на комментарии вежливо и по делу.
4. После двух апрувов и зелёного CI PR мержит автор (или ответственный, если настроен branch protection).
