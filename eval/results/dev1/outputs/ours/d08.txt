# Процесс код-ревью (Code Review)

## Зачем нужно ревью

Код-ревью — не формальность. Через него команда делится знаниями, ловит баги до прода и держит качество кодовой базы. Относитесь к нему как к асинхронному парному программированию: вместе делаем продукт лучше.

## Кто смотрит PR

Каждый Pull Request перед мержем должен получить минимум два апрува. Одного недостаточно, даже если изменения простые.

Один из ревьюеров должен быть из другой команды. Так мы не застреваем в «туннельном зрении», раньше находим проблемы интеграции и переносим практики между отделами. Свежий взгляд замечает то, к чему свои привыкли.

Например, если вы из Backend, один из ревьюеров должен быть из Frontend, Mobile, Data, DevOps или любой другой команды.

## Размер PR

Если в PR больше 400 строк изменений, разбейте его на несколько логических PR. Автогенерированный код, lock-файлы, миграции БД и конфиги не считаются.

Большой PR сложно проверить качественно: внимание ревьюера падает после 200–300 строк. Риск пропустить критичный баг растёт экспоненциально. Долгое ревью блокирует коллег и замедляет доставку фич.

Исключения: срочные хотфиксы в прод и крупный рефакторинг инфраструктуры (по согласованию с техлидом).

Если не получается уложиться в 400 строк, вынесите подготовительные изменения (рефакторинг, подготовку тестов) в отдельный PR, а основную логику — в следующий.

## Когда можно мержить

Мержить PR в пятницу после 16:00 по локальному времени офиса запрещено. После выката нужно время на мониторинг, а если что-то сломается, реагировать будет некому. Выходные не предназначены для дежурств по проду.

Крупные фичи мержьте до пятницы 16:00 или в понедельник. Мелкие багфиксы можно, если вы уверены на 100% и есть кто-то из дежурных.

## Чек-лист для автора PR

Перед созданием PR проверьте:
- [ ] PR меньше 400 строк (или есть задокументированное исключение)
- [ ] В описании понятно, что делает код и зачем (со ссылкой на тикет)
- [ ] Для UI-изменений добавлены скриншоты или видео
- [ ] Тесты добавлены или обновлены (или объяснено, почему они не нужны)
- [ ] Запрошены минимум 2 ревьюера, один из другой команды
- [ ] CI зелёный, линтеры прошли
- [ ] Вы сами посмотрели diff перед публикацией

## Чек-лист для ревьюера

При ревью проверьте:
- [ ] Код решает заявленную задачу, а не «просто работает»
- [ ] Нет очевидных багов, утечек памяти, N+1 запросов
- [ ] Соблюдены стандарты кодирования команды
- [ ] Критичная логика покрыта тестами
- [ ] Документация и комментарии обновлены (если менялся API)
- [ ] В коде нет секретов, токенов и персональных данных
- [ ] Изменения не ломают смежные модули (особенно важно для кросс-командного ревью)

SLA: постарайтесь посмотреть PR в течение одного рабочего дня. Если не успеваете, напишите об этом автору.

## Процесс по шагам

1. Автор создаёт PR и назначает ревьюеров (минимум 2, один из другой команды).
2. Ревьюеры оставляют комментарии и выставляют `Approve` или `Request changes`.
3. Автор исправляет замечания и отвечает на комментарии вежливо и по делу.
4. Когда есть два апрува и зелёный CI, автор мержит PR (или мержит ответственный, если настроен branch protection).
