# Процесс код-ревью (Code Review)

## Зачем нужно ревью

Код-ревью помогает делиться знаниями, ловить баги до прода и держать качество кодовой базы. Это асинхронное парное программирование: вместе делаем продукт лучше.

## Кто смотрит PR

Каждый Pull Request должен получить минимум два апрува перед мержем. Одного мало, даже если изменения «простые».

Один из ревьюеров обязательно должен быть из другой команды. Так мы:
- избегаем «туннельного зрения» внутри команды;
- раньше находим проблемы интеграции;
- обмениваемся лучшими практиками между отделами;
- получаем свежий взгляд на то, к чему «свои» привыкли.

Например, если вы из Backend, одним из ревьюеров должен быть человек из Frontend, Mobile, Data, DevOps или другой команды.

## Размер PR: правило 400 строк

Если в PR больше 400 строк изменений, разбейте его на несколько логических PR. Автогенерированный код, lock-файлы, миграции БД и конфиги не считаются.

Большие PR сложно проверить качественно: внимание ревьюера падает после 200–300 строк. Риск пропустить критичный баг растёт экспоненциально. Долгое ревью блокирует коллег и замедляет доставку фич.

Исключения: срочные хотфиксы в прод и крупный рефакторинг инфраструктуры (по согласованию с техлидом).

Если не получается уложиться в 400 строк, вынесите подготовительные изменения (рефакторинг, подготовку тестов) в отдельный PR, а основную логику сделайте в следующем.

## Когда можно мержить

Мержить PR в пятницу после 16:00 по локальному времени офиса запрещено. После выката нужно время на мониторинг, а если что-то сломается, некому быстро реагировать. Выходные не предназначены для дежурств по проду.

Крупные фичи мержьте до 16:00 в пятницу или в понедельник. Мелкие багфиксы можно, если вы уверены на 100% и есть кто-то из дежурных.

## Чек-лист для автора PR

Перед созданием PR убедитесь:
- [ ] PR меньше 400 строк (или исключение задокументировано)
- [ ] В описании понятно, что делает код и зачем (со ссылкой на тикет)
- [ ] Для UI-изменений добавлены скриншоты или видео
- [ ] Добавлены или обновлены тесты (или обосновано, почему они не нужны)
- [ ] Запрошены ревьюеры: минимум 2 человека, один из другой команды
- [ ] CI зелёный, линтеры прошли
- [ ] Вы сами посмотрели diff перед публикацией

## Чек-лист для ревьюера

При ревью проверяйте:
- [ ] Код решает заявленную задачу, а не «просто работает»
- [ ] Нет очевидных багов, утечек памяти, N+1 запросов
- [ ] Соблюдены стандарты кодирования команды
- [ ] Критичная логика покрыта тестами
- [ ] Документация и комментарии обновлены (если менялся API)
- [ ] Нет секретов, токенов или персональных данных в коде
- [ ] Изменения не ломают смежные модули (особенно важно для кросс-командного ревью)

SLA: постарайтесь посмотреть PR в течение одного рабочего дня. Если не успеваете, отпишитесь автору.

## Процесс по шагам

1. Автор создаёт PR и назначает ревьюеров (минимум 2, один из другой команды).
2. Ревьюеры оставляют комментарии и выставляют `Approve` или `Request changes`.
3. Автор исправляет замечания и отвечает на комментарии вежливо и по делу.
4. После двух апрувов и зелёного CI автор мержит PR (или мержит ответственный, если настроен branch protection).
