# Процесс код-ревью (Code Review)

## Философия

Код-ревью помогает делиться знаниями, ловить баги до прода и держать качество кодовой базы. Относимся к нему как к асинхронному парному программированию: вместе делаем продукт лучше.

## Кто смотрит PR

### Правило двух ревьюеров

Каждый Pull Request должен получить минимум два апрува перед мержем. Одного мало, даже если изменения простые.

### Кросс-командное ревью

Один из ревьюеров должен быть из другой команды. Это нужно, чтобы:

- не поймать «туннельное зрение» внутри команды;
- находить проблемы интеграции на раннем этапе;
- распространять лучшие практики между отделами;
- получать свежий взгляд на то, к чему привыкли «свои».

Пример: если вы из Backend, один из ревьюеров должен быть из Frontend, Mobile, Data, DevOps или любой другой команды.

## Размер PR: правило 400 строк

Если в PR больше 400 строк изменений (не считая автогенерированный код, lock-файлы, миграции БД и конфиги), разбейте его на несколько логических PR.

Почему это важно:

- большие PR сложно проверить качественно: внимание ревьюера падает после 200–300 строк;
- риск пропустить критичный баг растёт экспоненциально;
- долгое ревью блокирует коллег и замедляет доставку фич.

Исключения: срочные хотфиксы в прод и крупный рефакторинг инфраструктуры (по согласованию с техлидом).

Если в 400 строк не укладывается, вынесите подготовительные изменения (рефакторинг, подготовку тестов) в отдельный PR, а основную логику оставьте для следующего.

## Когда можно мержить

### Запрет на пятничный деплой

Мержить PR в пятницу после 16:00 по локальному времени офиса запрещено.

Почему:

- на мониторинг после выката не хватит времени;
- если что-то сломается, оперативно реагировать будет некому;
- выходные не предназначены для дежурств по проду.

Что делать:

- мерж крупных фич планируйте до пятницы 16:00 или на понедельник;
- мелкие багфиксы можно мержить, если вы уверены на 100% и на связи кто-то из дежурных.

## Чек-лист для автора PR

Перед созданием PR убедитесь, что:

- [ ] PR меньше 400 строк (или есть задокументированное исключение);
- [ ] в описании понятно, что делает код и зачем (со ссылкой на тикет);
- [ ] для UI-изменений добавлены скриншоты или видео;
- [ ] тесты добавлены или обновлены (или обосновано, почему они не нужны);
- [ ] запрошены минимум два ревьюера, один из другой команды;
- [ ] CI зелёный, линтеры прошли;
- [ ] вы сами посмотрели diff перед публикацией.

## Чек-лист для ревьюера

При ревью проверьте:

- [ ] код решает заявленную задачу, а не «просто работает»;
- [ ] в нём нет очевидных багов, утечек памяти и N+1 запросов;
- [ ] соблюдены стандарты кодирования команды;
- [ ] критичная логика покрыта тестами;
- [ ] документация и комментарии обновлены, если менялся API;
- [ ] в коде нет секретов, токенов и персональных данных;
- [ ] изменения не ломают смежные модули (особенно важно при кросс-командном ревью).

SLA: постарайтесь посмотреть PR в течение одного рабочего дня. Если не успеваете, отпишитесь автору.

## Процесс по шагам

1. Автор создаёт PR и назначает ревьюеров (минимум двух, один из другой команды).
2. Ревьюеры оставляют комментарии и выставляют `Approve` или `Request changes`.
3. Автор исправляет замечания и отвечает на комментарии вежливо и по делу.
4. После двух апрувов и зелёного CI мержит автор (или ответственный, если настроен branch protection).
