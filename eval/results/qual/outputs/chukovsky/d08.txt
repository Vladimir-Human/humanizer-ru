# Процесс код-ревью (Code Review)

## Философия
Код-ревью нужно не для галочки. Оно помогает делиться знаниями, ловить баги до прода и держать кодовую базу в порядке. Относитесь к ревью как к асинхронному парному программированию: вместе мы делаем продукт лучше.

---

## Кто смотрит PR

### Правило двух ревьюеров
Каждый Pull Request должен получить **минимум два апрува** перед мержем. Одного мало, даже если изменения «простые».

### Кросс-командное ревью (обязательно)
**Один из ревьюеров должен быть из другой команды.**

Зачем:
- Так мы не застреваем в «туннельном зрении» внутри команды.
- Проблемы интеграции находятся раньше.
- Лучшие практики расходятся между отделами.
- Свежий взгляд замечает то, к чему «свои» уже привыкли.

> 💡 **Пример:** если вы из Backend, один из ревьюеров должен быть из Frontend, Mobile, Data, DevOps или любой другой команды.

---

## Размер PR: правило 400 строк

Если в вашем PR **больше 400 строк изменений** (автогенерированный код, lock-файлы, миграции БД и конфиги не считаются), **пожалуйста, разбейте его на несколько логических PR**.

**Почему это важно:**
- Большой PR трудно проверить качественно: после 200–300 строк внимание ревьюера падает.
- Чем больше diff, тем выше риск пропустить серьёзный баг.
- Долгое ревью блокирует коллег и замедляет выкатку фич.

**Исключения:** срочные хотфиксы в прод и крупный рефакторинг инфраструктуры (по согласованию с техлидом).

> 🛠 **Совет:** если в 400 строк не укладываетесь, вынесите подготовительные изменения (рефакторинг, подготовку тестов) в отдельный PR, а основную логику оставьте для следующего.

---

## Когда можно мержить

### ⛔ Никаких пятничных деплоев
**Мержить PR в пятницу после 16:00 (по локальному времени офиса) запрещено.**

Почему:
- После выката не хватит времени на мониторинг.
- Если что-то сломается, оперативно реагировать будет некому.
- Выходные не созданы для дежурств по проду.

Что делать:
- Крупные фичи мержите **до пятницы 16:00** или в **понедельник**.
- Мелкие багфиксы можно мержить, если вы уверены на 100% и на связи кто-то из дежурных.

## Чек-лист для автора PR

Перед созданием PR убедитесь, что:
- [ ] В PR меньше 400 строк (или есть оформленное исключение).
- [ ] В описании понятно, что делает код и **зачем** (со ссылкой на тикет).
- [ ] Для UI-изменений добавлены скриншоты или видео.
- [ ] Тесты добавлены или обновлены (или объяснено, почему они не нужны).
- [ ] Запрошены ревьюеры: **минимум два человека**, один из другой команды.
- [ ] CI зелёный, линтеры прошли.
- [ ] Вы сами просмотрели diff перед публикацией.

---

## Чек-лист для ревьюера

При ревью проверьте, что:
- [ ] Код решает заявленную задачу, а не «просто работает».
- [ ] В нём нет очевидных багов, утечек памяти и N+1 запросов.
- [ ] Соблюдены стандарты кодирования команды.
- [ ] Критичная логика покрыта тестами.
- [ ] Документация и комментарии обновлены (если менялся API).
- [ ] В коде нет секретов, токенов и персональных данных.
- [ ] Изменения не ломают смежные модули (для кросс-командного ревью это особенно важно).

**SLA:** старайтесь посмотреть PR в течение **одного рабочего дня**. Если не успеваете, напишите автору.

---

1. **Автор** создаёт PR и назначает ревьюеров (минимум двух, один из другой команды).
