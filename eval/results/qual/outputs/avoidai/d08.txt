# Процесс код-ревью (Code Review)

## Философия
Код-ревью — это не формальная галочка, а способ делиться знаниями, ловить баги до прода и держать качество кодовой базы на уровне. Относимся к ревью как к асинхронному парному программированию: вместе делаем продукт лучше.

---

## Кто смотрит PR

### Правило двух ревьюеров
Каждый Pull Request должен получить **минимум два апрува** перед мержем. Один апрув — недостаточно, даже если изменения «простые».

### Кросс-командное ревью (обязательно)
**Один из ревьюеров должен быть из другой команды.**

Зачем это нужно:
- Избегаем «туннельного зрения» внутри команды
- Находим проблемы интеграции на раннем этапе
- Распространяем лучшие практики между отделами
- Свежий взгляд ловит то, к чему привыкли «свои»

> 💡 **Пример:** Если вы из команды Backend, один из ревьюеров должен быть из Frontend, Mobile, Data, DevOps или любой другой команды.

---

## Размер PR: правило 400 строк

Если ваш PR содержит **более 400 строк изменений** (не считая автогенерированный код, lock-файлы, миграции БД и конфиги), **пожалуйста, разбейте его на несколько логических PR**.

**Почему это критично:**
- Большие PR сложно проверить качественно — внимание ревьюера падает после 200–300 строк
- Риск пропустить критичный баг растёт экспоненциально
- Долгое ревью блокирует коллег и замедляет доставку фич

**Исключения:** срочные хотфиксы в прод, крупный рефакторинг инфраструктуры (по согласованию с техлидом).

> 🛠 **Совет:** Если не получается уложиться в 400 строк — вынесите подготовительные изменения (рефакторинг, подготовку тестов) в отдельный PR, а основную логику — в следующий.

---

## Когда можно мержить

### ⛔ Запрет на пятничный деплой
**Запрещено мержить PR в пятницу после 16:00** (по локальному времени офиса).

**Почему:**
- Недостаточно времени для мониторинга после выката
- Если что-то сломается — некому оперативно реагировать
- Выходные не предназначены для дежурств по проду

**Что делать:**
- Планируйте мерж крупных фич **до пятницы 16:00** или на **понедельник**
- Мелкие багфиксы — можно, если уверены на 100% и есть кто-то из дежурных

## Чек-лист для автора PR

Перед созданием PR убедитесь:
- [ ] PR меньше 400 строк (или есть documented исключение)
- [ ] Описание понятно: что делает код и **зачем** (ссылка на тикет)
- [ ] Для UI-изменений: добавлены скриншоты/видео
- [ ] Добавлены/обновлены тесты (или обосновано, почему не нужны)
- [ ] Запрошены ревьюеры: **минимум 2 человека**, один из другой команды
- [ ] CI зелёный, линтеры прошли
- [ ] Проведена самопроверка: вы сами посмотрели diff перед публикацией

---

## Чек-лист для ревьюера

При ревью проверяйте:
- [ ] Код решает заявленную задачу, а не «просто работает»
- [ ] Нет очевидных багов, утечек памяти, N+1 запросов
- [ ] Соблюдены стандарты кодирования команды
- [ ] Критичная логика покрыта тестами
- [ ] Документация/комментарии обновлены (если менялся API)
- [ ] Нет секретов, токенов или персональных данных в коде
- [ ] Изменения не ломают смежные модули (особенно важно для кросс-командного ревью)

**SLA:** Постарайтесь посмотреть PR в течение **одного рабочего дня**. Если не успеваете — отпишитесь автору.

---
