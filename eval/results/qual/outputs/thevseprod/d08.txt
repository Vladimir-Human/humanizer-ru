# Процесс код-ревью (Code Review)

## Философия
Код-ревью помогает делиться знаниями, ловить баги до прода и держать качество кодовой базы. Относимся к ревью как к асинхронному парному программированию.

---

## Кто смотрит PR

### Правило двух ревьюеров
Каждый Pull Request должен получить минимум **два апрува** перед мержем. Одного апрува недостаточно, даже если изменения «простые».

### Кросс-командное ревью (обязательно)
Один из ревьюеров должен быть из другой команды.

- Команда не застревает в «туннельном зрении»
- Проблемы интеграции находятся раньше
- Лучшие практики расходятся между отделами
- Свежий взгляд ловит то, к чему привыкли «свои»

> Пример: если вы из команды Backend, один из ревьюеров должен быть из Frontend, Mobile, Data, DevOps или любой другой команды.

---

## Размер PR: правило 400 строк

Если в вашем PR **больше 400 строк** изменений (автогенерированный код, lock-файлы, миграции БД и конфиги не считаются), пожалуйста, разбейте его на несколько логических PR.

Большие PR сложно проверить качественно: внимание ревьюера падает после 200-300 строк. Риск пропустить критичный баг растёт экспоненциально. Долгое ревью блокирует коллег и замедляет доставку фич.

Исключения: срочные хотфиксы в прод и крупный рефакторинг инфраструктуры (по согласованию с техлидом).

> Совет: если не получается уложиться в 400 строк, вынесите подготовительные изменения (рефакторинг, подготовку тестов) в отдельный PR, а основную логику оставьте для следующего.

---

## Когда можно мержить

### Запрет на пятничный деплой
Мержить PR в пятницу после **16:00** (по локальному времени офиса) запрещено.

После выката остаётся мало времени на мониторинг, а если что-то сломается, оперативно реагировать некому. Выходные не предназначены для дежурств по проду.

Крупные фичи мержите до пятницы 16:00 или в понедельник. Мелкие багфиксы можно, если вы уверены на 100% и на связи есть кто-то из дежурных.

## Чек-лист для автора PR

Перед созданием PR убедитесь:
- [ ] PR меньше 400 строк (или есть задокументированное исключение)
- [ ] Из описания понятно, что делает код и зачем (ссылка на тикет)
- [ ] Для UI-изменений добавлены скриншоты или видео
- [ ] Тесты добавлены или обновлены (или обосновано, почему не нужны)
- [ ] Запрошены ревьюеры: минимум **2 человека**, один из другой команды
- [ ] CI зелёный, линтеры прошли
- [ ] Самопроверка: вы сами посмотрели diff перед публикацией

---

## Чек-лист для ревьюера

При ревью проверяйте:
- [ ] Код решает заявленную задачу, а не «просто работает»
- [ ] Нет очевидных багов, утечек памяти, N+1 запросов
- [ ] Соблюдены стандарты кодирования команды
- [ ] Критичная логика покрыта тестами
- [ ] Документация и комментарии обновлены (если менялся API)
- [ ] Нет секретов, токенов или персональных данных в коде
- [ ] Изменения не ломают смежные модули (особенно важно для кросс-командного ревью)

SLA: постарайтесь посмотреть PR в течение **одного рабочего дня**. Если не успеваете, отпишитесь автору.

---
