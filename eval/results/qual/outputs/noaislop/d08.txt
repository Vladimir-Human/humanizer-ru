# Процесс код-ревью

Код-ревью помогает делиться знаниями, ловить баги до прода и держать качество кодовой базы. Относимся к нему как к асинхронному парному программированию.

## Кто смотрит PR

### Два ревьюера

Каждый Pull Request должен получить минимум два апрува перед мержем. Одного мало, даже если изменения простые.

### Ревьюер из другой команды

Один из ревьюеров должен быть из другой команды. Зачем:

- Команда перестаёт смотреть на код через одни и те же шоры.
- Проблемы интеграции находятся раньше.
- Хорошие практики расходятся между отделами.
- Новый человек замечает то, к чему свои уже привыкли.

Например, если вы из Backend, один из ревьюеров должен быть из Frontend, Mobile, Data, DevOps или другой команды.

## Размер PR: 400 строк

Если в PR больше 400 строк изменений, разбейте его на несколько логических PR. Автогенерированный код, lock-файлы, миграции БД и конфиги не считаются.

Почему так:

- Большой PR сложно проверить качественно. После 200–300 строк внимание ревьюера падает.
- Чем больше PR, тем выше риск пропустить критичный баг.
- Долгое ревью блокирует коллег и замедляет доставку фич.

Исключения: срочные хотфиксы в прод и крупный рефакторинг инфраструктуры (по согласованию с техлидом).

Если не получается уложиться в 400 строк, вынесите подготовительные изменения (рефакторинг, подготовку тестов) в отдельный PR, а основную логику отправьте следующим.

## Когда можно мержить

В пятницу после 16:00 по локальному времени офиса мержить PR запрещено. Причины:

- На мониторинг после выката не хватит времени.
- Если что-то сломается, оперативно реагировать будет некому.
- Никто не должен дежурить по проду в выходные.

Крупные фичи мержите до 16:00 в пятницу или в понедельник. Мелкие багфиксы можно мержить, если вы уверены на 100% и на связи кто-то из дежурных.

## Чек-лист для автора PR

Перед созданием PR проверьте:

- [ ] PR меньше 400 строк (или есть задокументированное исключение)
- [ ] В описании сказано, что делает код и зачем (со ссылкой на тикет)
- [ ] Для UI-изменений добавлены скриншоты или видео
- [ ] Тесты добавлены или обновлены (или написано, почему они не нужны)
- [ ] Запрошены минимум два ревьюера, один из другой команды
- [ ] CI зелёный, линтеры прошли
- [ ] Вы сами посмотрели diff перед публикацией

## Чек-лист для ревьюера

При ревью проверьте:

- [ ] Код решает заявленную задачу, а не «просто работает»
- [ ] Нет очевидных багов, утечек памяти, N+1 запросов
- [ ] Соблюдены стандарты кодирования команды
- [ ] Критичная логика покрыта тестами
- [ ] Документация и комментарии обновлены (если менялся API)
- [ ] В коде нет секретов, токенов и персональных данных
- [ ] Изменения не ломают смежные модули (особенно для ревьюера из другой команды)

SLA: посмотрите PR в течение одного рабочего дня. Если не успеваете, напишите автору.

## Процесс по шагам

1. Автор создаёт PR и назначает ревьюеров (минимум два, один из другой команды).
2. Ревьюеры оставляют комментарии и выставляют `Approve` или `Request changes`.
3. Автор исправляет замечания и отвечает на комментарии вежливо и по делу.
4. После двух апрувов и зелёного CI автор мержит PR. Если настроен branch protection, мержит ответственный.
