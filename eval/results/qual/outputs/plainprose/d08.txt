# Процесс код-ревью

Код-ревью нужно, чтобы делиться знаниями, ловить баги до прода и держать качество кодовой базы. Относитесь к нему как к асинхронному парному программированию.

## Кто смотрит PR

Каждый Pull Request получает минимум два апрува перед мержем. Один апрув недостаточен, даже если изменения простые.

Один из ревьюеров должен быть из другой команды. Если вы из Backend, позовите кого-то из Frontend, Mobile, Data, DevOps или другой команды. Так мы:

- не застреваем в «туннельном зрении» внутри команды;
- находим проблемы интеграции раньше;
- переносим удачные практики из отдела в отдел;
- получаем взгляд человека, который не привык к вашему коду.

## Размер PR

Если в PR больше 400 строк изменений, разбейте его на несколько логических PR. Автогенерированный код, lock-файлы, миграции БД и конфиги не считаются.

Причины:

- Большой PR трудно проверить внимательно: после 200–300 строк внимание ревьюера падает.
- Чем больше PR, тем выше риск пропустить критичный баг.
- Долгое ревью блокирует коллег и замедляет доставку фич.

Исключения: срочные хотфиксы в прод и крупный рефакторинг инфраструктуры (по согласованию с техлидом).

Если в 400 строк не укладывается, вынесите подготовительные изменения (рефакторинг, подготовку тестов) в отдельный PR, а основную логику отправьте следующим.

## Когда можно мержить

Мержить PR в пятницу после 16:00 по локальному времени офиса нельзя. Причины:

- после выката не хватит времени на мониторинг;
- если что-то сломается, оперативно реагировать будет некому;
- выходные не предназначены для дежурств по проду.

Крупные фичи мержите до пятницы 16:00 или в понедельник. Мелкие багфиксы можно мержить и позже, если вы уверены в них на 100% и на связи есть кто-то из дежурных.

## Чек-лист автора PR

Перед созданием PR проверьте:

- [ ] В PR меньше 400 строк или есть задокументированное исключение
- [ ] В описании написано, что делает код и зачем (со ссылкой на тикет)
- [ ] Для UI-изменений приложены скриншоты или видео
- [ ] Тесты добавлены или обновлены, либо описано, почему они не нужны
- [ ] Запрошены минимум два ревьюера, один из другой команды
- [ ] CI зелёный, линтеры прошли
- [ ] Вы сами посмотрели diff перед публикацией

## Чек-лист ревьюера

При ревью проверьте:

- [ ] Код решает заявленную задачу, а не «просто работает»
- [ ] В нём нет очевидных багов, утечек памяти и N+1 запросов
- [ ] Соблюдены стандарты кодирования команды
- [ ] Критичная логика покрыта тестами
- [ ] Документация и комментарии обновлены, если менялся API
- [ ] В коде нет секретов, токенов и персональных данных
- [ ] Изменения не ломают смежные модули (особенно важно при кросс-командном ревью)

SLA: посмотрите PR в течение одного рабочего дня. Если не успеваете, напишите автору.

## Процесс по шагам

1. Автор создаёт PR и назначает ревьюеров: минимум двух, один из другой команды.
2. Ревьюеры оставляют комментарии и ставят `Approve` или `Request changes`.
3. Автор исправляет замечания и отвечает на комментарии вежливо и по делу.
4. После двух апрувов и зелёного CI автор мержит. Если настроен branch protection, мержит ответственный.
