# Процесс код-ревью

Код-ревью помогает делиться знаниями, ловить баги до прода и держать качество кодовой базы. Относитесь к нему как к асинхронному парному программированию.

## Кто смотрит PR

Каждый Pull Request должен получить минимум два апрува перед мержем. Одного мало, даже если изменения кажутся простыми.

Один из ревьюеров должен быть из другой команды. Так мы не застреваем в туннельном зрении внутри команды, раньше находим проблемы интеграции и переносим лучшие практики между отделами. Свежий взгляд замечает то, к чему «свои» привыкли. Например, если вы из Backend, позовите кого-нибудь из Frontend, Mobile, Data, DevOps или другой команды.

## Размер PR: правило 400 строк

Если в PR больше 400 строк изменений (без автогенерированного кода, lock-файлов, миграций БД и конфигов), разбейте его на несколько логических PR.

Большие PR сложно проверить качественно: после 200–300 строк внимание ревьюера падает, и риск пропустить серьёзный баг растёт. Долгое ревью к тому же блокирует коллег и замедляет доставку фич.

Исключения: срочные хотфиксы в прод и крупный рефакторинг инфраструктуры (по согласованию с техлидом).

Если в 400 строк не укладывается, вынесите подготовительные изменения, такие как рефакторинг и подготовку тестов, в отдельный PR, а основную логику отправьте следующим.

## Когда можно мержить

Мержить PR в пятницу после 16:00 по локальному времени офиса запрещено. После выката нужно время на мониторинг, а если что-то сломается, оперативно реагировать будет некому. Выходные не предназначены для дежурств по проду.

Крупные фичи мержите до пятницы 16:00 или в понедельник. Мелкие багфиксы можно мержить и позже, если вы уверены в них на 100% и на связи есть кто-то из дежурных.

## Чек-лист для автора PR

Перед созданием PR убедитесь, что:

- [ ] PR меньше 400 строк (или есть задокументированное исключение)
- [ ] В описании сказано, что делает код и зачем, со ссылкой на тикет
- [ ] Для UI-изменений добавлены скриншоты или видео
- [ ] Тесты добавлены или обновлены (или объяснено, почему они не нужны)
- [ ] Запрошены минимум два ревьюера, один из другой команды
- [ ] CI зелёный, линтеры прошли
- [ ] Вы сами посмотрели diff перед публикацией

## Чек-лист для ревьюера

При ревью проверьте, что:

- [ ] Код решает заявленную задачу, а не «просто работает»
- [ ] В нём нет очевидных багов, утечек памяти и N+1 запросов
- [ ] Соблюдены стандарты кодирования команды
- [ ] Критичная логика покрыта тестами
- [ ] Документация и комментарии обновлены, если менялся API
- [ ] В коде нет секретов, токенов и персональных данных
- [ ] Изменения не ломают смежные модули (особенно важно при кросс-командном ревью)

Постарайтесь посмотреть PR в течение одного рабочего дня. Если не успеваете, напишите автору.

## Процесс по шагам

1. Автор создаёт PR и назначает ревьюеров: минимум двух, один из другой команды.
2. Ревьюеры оставляют комментарии и выставляют `Approve` или `Request changes`.
3. Автор исправляет замечания и отвечает на комментарии вежливо и по делу.
4. После двух апрувов и зелёного CI мержит автор. Если настроен branch protection, мержит ответственный.
