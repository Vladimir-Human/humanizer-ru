# Процесс код-ревью (Code Review)

## Философия
Код-ревью нужно, чтобы делиться знаниями, ловить баги до прода и держать качество кодовой базы. Относимся к ревью как к асинхронному парному программированию.

---

## Кто смотрит PR

### Правило двух ревьюеров
Каждый Pull Request должен получить **минимум два апрува** перед мержем. Одного апрува недостаточно, даже если изменения «простые».

### Кросс-командное ревью (обязательно)
**Один из ревьюеров должен быть из другой команды.**

Зачем:
- Избегаем «туннельного зрения» внутри команды
- Находим проблемы интеграции на раннем этапе
- Распространяем лучшие практики между отделами
- Свежий взгляд ловит то, к чему привыкли «свои»

> **Пример.** Если вы из команды Backend, один из ревьюеров должен быть из Frontend, Mobile, Data, DevOps или любой другой команды.

---

## Размер PR: правило 400 строк

Если в PR **больше 400 строк изменений** (автогенерированный код, lock-файлы, миграции БД и конфиги не считаются), разбейте его на несколько логических PR.

Почему:
- Большие PR сложно проверить качественно: внимание ревьюера падает после 200–300 строк
- Чем больше PR, тем выше риск пропустить критичный баг
- Долгое ревью блокирует коллег и замедляет доставку фич

**Исключения:** срочные хотфиксы в прод, крупный рефакторинг инфраструктуры (по согласованию с техлидом).

> **Совет.** Если не получается уложиться в 400 строк, вынесите подготовительные изменения (рефакторинг, подготовку тестов) в отдельный PR, а основную логику оставьте для следующего.

---

## Когда можно мержить

### Запрет на пятничный деплой
**Мержить PR в пятницу после 16:00 (по локальному времени офиса) запрещено.**

Почему:
- Не хватит времени на мониторинг после выката
- Если что-то сломается, оперативно реагировать будет некому
- Выходные не предназначены для дежурств по проду

Что делать:
- Крупные фичи мержите **до пятницы 16:00** или в **понедельник**
- Мелкие багфиксы можно, если вы уверены на 100% и на связи есть кто-то из дежурных

## Чек-лист для автора PR

Перед созданием PR убедитесь:
- [ ] В PR меньше 400 строк (или есть задокументированное исключение)
- [ ] Описание объясняет, что делает код и **зачем** (со ссылкой на тикет)
- [ ] Для UI-изменений добавлены скриншоты или видео
- [ ] Тесты добавлены или обновлены (или обосновано, почему не нужны)
- [ ] Запрошены ревьюеры: **минимум 2 человека**, один из другой команды
- [ ] CI зелёный, линтеры прошли
- [ ] Вы сами посмотрели diff перед публикацией

---

## Чек-лист для ревьюера

При ревью проверьте:
- [ ] Код решает заявленную задачу, а не «просто работает»
- [ ] Нет очевидных багов, утечек памяти, N+1 запросов
- [ ] Соблюдены стандарты кодирования команды
- [ ] Критичная логика покрыта тестами
- [ ] Документация и комментарии обновлены (если менялся API)
- [ ] В коде нет секретов, токенов и персональных данных
- [ ] Изменения не ломают смежные модули (особенно важно для кросс-командного ревью)

**SLA:** посмотрите PR в течение **одного рабочего дня**. Если не успеваете, напишите автору.

---
