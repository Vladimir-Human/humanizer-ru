# Процесс код-ревью

## Философия

Код-ревью нужно, чтобы делиться знаниями, ловить баги до прода и держать качество кодовой базы. Считайте его асинхронным парным программированием: вместе делаем продукт лучше.

## Кто смотрит PR

Каждый Pull Request должен получить минимум два апрува перед мержем. Одного мало, даже если изменения простые.

Один из ревьюеров должен быть из другой команды. Так мы:
- не застреваем в туннельном зрении внутри команды;
- раньше находим проблемы интеграции;
- переносим хорошие практики между отделами;
- получаем свежий взгляд на то, к чему свои уже привыкли.

Например, если вы из Backend, одним из ревьюеров должен быть человек из Frontend, Mobile, Data, DevOps или другой команды.

## Размер PR: правило 400 строк

Если в PR больше 400 строк изменений, разбейте его на несколько логических PR. Автогенерированный код, lock-файлы, миграции БД и конфиги не считаются.

Почему так:
- большой PR трудно проверить качественно, после 200–300 строк внимание ревьюера падает;
- растёт риск пропустить критичный баг;
- долгое ревью блокирует коллег и замедляет доставку фич.

Исключения: срочные хотфиксы в прод и крупный рефакторинг инфраструктуры (по согласованию с техлидом).

Если не получается уложиться в 400 строк, вынесите подготовительные изменения (рефакторинг, подготовку тестов) в отдельный PR, а основную логику отправьте следующим.

## Когда можно мержить

Мержить PR в пятницу после 16:00 по локальному времени офиса нельзя. Причины:
- после выката не хватит времени понаблюдать за продом;
- если что-то сломается, оперативно реагировать будет некому;
- выходные не предназначены для дежурств по проду.

Крупные фичи мержите до пятницы 16:00 или в понедельник. Мелкие багфиксы можно, если вы уверены на 100% и на связи кто-то из дежурных.

## Чек-лист для автора PR

Перед созданием PR проверьте:
- [ ] В PR меньше 400 строк (или есть описанное исключение)
- [ ] В описании понятно, что делает код и зачем (со ссылкой на тикет)
- [ ] Для UI-изменений добавлены скриншоты или видео
- [ ] Тесты добавлены или обновлены (или объяснено, почему они не нужны)
- [ ] Запрошены минимум два ревьюера, один из другой команды
- [ ] CI зелёный, линтеры прошли
- [ ] Вы сами посмотрели diff перед публикацией

## Чек-лист для ревьюера

При ревью проверьте:
- [ ] Код решает заявленную задачу, а не «просто работает»
- [ ] Нет очевидных багов, утечек памяти, N+1 запросов
- [ ] Соблюдены стандарты кодирования команды
- [ ] Критичная логика покрыта тестами
- [ ] Документация и комментарии обновлены, если менялся API
- [ ] В коде нет секретов, токенов и персональных данных
- [ ] Изменения не ломают смежные модули (для кросс-командного ревью это особенно важно)

SLA: постарайтесь посмотреть PR в течение рабочего дня. Если не успеваете, напишите автору.

## Процесс по шагам

1. Автор создаёт PR и назначает ревьюеров (минимум двух, один из другой команды).
2. Ревьюеры оставляют комментарии и ставят `Approve` или `Request changes`.
3. Автор исправляет замечания и отвечает на комментарии вежливо и по делу.
