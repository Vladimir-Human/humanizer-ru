## Что такое кэш и зачем нам Redis

Для новичков: **кэш** — это временное хранилище для часто нужных данных. Он позволяет не ходить за ними каждый раз в «дорогие» места: базу данных, внешние сервисы или тяжёлые вычисления.

Если проще: когда ответ на один и тот же вопрос можно быстро достать из памяти, незачем каждый раз считать его с нуля.

---

## Зачем нам Redis

**Redis** — быстрый кэш и хранилище в памяти. Мы держим в нём готовые ответы API и промежуточные данные, но ненадолго.

Эффект можно измерить:

- API без кэша: **~800 мс**
- API с Redis: **~40 мс**

Выходит, с кэшем ответы приходят примерно **в 20 раз быстрее**.

Для пользователя это значит, что интерфейс открывается почти мгновенно. Для системы — что база данных и внешние сервисы нагружены меньше.

---

## Как это выглядит на практике

Допустим, пользователь часто запрашивает список товаров, профиль категории или какую-нибудь агрегированную информацию.

Без кэша каждый запрос идёт в базу:

```text
Запрос → проверка прав → запрос к базе → агрегация → ответ
```

С кэшем:

```text
Запрос → есть данные в Redis? → да → ответ
                         → нет → запрос к базе → сохранить в Redis → ответ
```

Если Redis отдаёт данные, мы не тратим время на обращение к базе и повторные вычисления.

---

## Сколько живёт кэш

У нас кэш живёт **10 минут**.

То есть данные, записанные в Redis, хранятся там максимум 10 минут, потом «протухают», и следующий запрос снова идёт в источник.

Например:

```text
00:00 — данные положили в Redis
00:05 — данные ещё актуальны
00:10 — данные истекли, следующий запрос пойдёт в базу
```

Это время жизни (TTL) подбирают так, чтобы найти баланс между скоростью и актуальностью данных.

---

## Почему нельзя кэшировать всё подряд

Кэш полезен, но обращаться с ним надо аккуратно.

Так делать не стоит:

- кэшировать данные, которые быстро меняются;
- показывать пользователям устаревшую информацию;
- кэшировать персональные данные, не разобравшись, кто и когда должен их видеть;
- кэшировать финансовые и платёжные операции.

Например, данные в базе уже изменились, а кэш живёт ещё 10 минут — пользователь увидит старую информацию. Поэтому для одних данных кэш не подходит вовсе, для других нужна аккуратная инвалидация.

---

## Главное исключение: платежи

**Данные о платежах мы никогда не кэшируем.**

Это важное правило. Платёжная информация не должна лежать в кэше, потому что:

- она слишком чувствительная;
- она должна быть актуальной на момент запроса;
- из-за кэша можно показать устаревшее или неверное состояние платежа;
- ошибки в платёжных данных могут стоить очень дорого.

Если ваш код, API, дашборд, аналитика или любой другой сценарий связан с платежами, не используйте Redis для кэширования таких ответов.

Правильное поведение:

```text
Платёжный запрос → всегда идти в источник данных → не сохранять в Redis
```

---

## Простая аналогия

Кэш — как шпаргалка рядом с учителем.

Если ученик часто задаёт один и тот же вопрос, учитель быстро заглядывает в шпаргалку. Но если вопрос про деньги и платежи, шпаргалке доверять нельзя: нужно сверяться с оригиналом.

Или ещё проще:

- API без кэша — каждый раз собирать пазл заново;
- Redis — заранее собранная картинка, которая хранится 10 минут;
- платежи — документы, которые нельзя брать из «картинки на 10 минут»: они должны быть точными прямо сейчас.

---

## Что помнить при разработке

1. **Redis ускоряет чтение данных.**
   Он особенно хорош для запросов, которые часто повторяются и которым не нужна идеальная свежесть до миллисекунды.

2. **Кэш — не источник истины.**
   Настоящие данные хранятся в базе или сервисе. Redis только ускоряет доступ к ним.

3. **TTL — 10 минут.**
   Данные в кэше могут быть не самыми свежими. Учитывайте это, когда проектируете UI и бизнес-логику.

4. **Платежи не кэшируем.**
   Никогда не кладите платёжные данные в Redis как в кэш. Это под запретом.

5. **Если данным критична свежесть, подумайте дважды.**
   Кэш уместен там, где задержка обновления в 10 минут допустима.

---

## Итог

Redis нужен нам, чтобы API работал быстро: вместо **800 мс** ответ занимает **40 мс**.

Мы кэшируем данные на **10 минут**, но **данные о платежах не кэшируем никогда**.

Простое правило:

```text
Обычные быстрые данные → можно кэшировать
Платежи → никогда не кэшировать
```
