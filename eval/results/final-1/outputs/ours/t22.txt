## Что такое кэш и зачем нам Redis

Для новичков: **кэш** — временное хранилище часто используемых данных. Он нужен, чтобы не запрашивать их каждый раз из «дорогих» мест: базы данных, внешних сервисов или тяжёлых вычислений.

Простыми словами: если ответ на один и тот же вопрос можно быстро взять из памяти, зачем считать его заново с нуля.

---

## Зачем нам Redis

Redis — быстрый кэш и хранилище в памяти. Мы держим в нём готовые ответы API или промежуточные данные на короткое время.

Эффект можно измерить:

- API без кэша: ~800 мс
- API с Redis: ~40 мс

Ответы получаются примерно в 20 раз быстрее. Для пользователя интерфейс загружается почти мгновенно, а база данных и внешние сервисы нагружаются меньше.

---

## Как это выглядит на практике

Допустим, пользователь часто запрашивает список товаров, профиль категории или какую-то агрегированную информацию.

Без кэша каждый запрос идёт в базу:

```text
Запрос → проверка прав → запрос к базе → агрегация → ответ
```

С кэшем:

```text
Запрос → есть данные в Redis? → да → ответ
                         → нет → запрос к базе → сохранить в Redis → ответ
```

Когда Redis возвращает данные, мы не обращаемся к базе и не повторяем вычисления.

---

## Сколько хранится кэш

У нас кэш живёт 10 минут. После записи в Redis данные хранятся там максимум 10 минут, затем «протухают», и следующий запрос снова идёт в источник данных.

Например:

```text
00:00 — данные положили в Redis
00:05 — данные ещё валидны
00:10 — данные истекли, следующий запрос пойдёт в базу
```

TTL (время жизни) выбирают так, чтобы найти баланс между скоростью и актуальностью данных.

---

## Что нельзя кэшировать

Кэш полезен, но использовать его нужно аккуратно.

Плохая практика:

- кэшировать данные, которые быстро меняются;
- показывать пользователям устаревшую информацию;
- кэшировать персональные данные, не понимая, кто и когда должен их видеть;
- кэшировать финансовые и платёжные операции.

Например, если данные изменили в базе, а кэш ещё живёт 10 минут, пользователь увидит старую информацию. Поэтому для некоторых данных кэш не подходит или требует аккуратной инвалидации.

---

## Главное исключение: платежи

**Данные о платежах мы никогда не кэшируем.**

Платёжная информация не должна храниться в кэше, потому что:

- она слишком чувствительная;
- она должна быть актуальной на момент запроса;
- из-за кэша можно показать устаревшее или неверное состояние платежа;
- ошибки в платёжных данных могут быть критичными.

Если ваш код, API, дашборд, аналитика или любой другой сценарий касается платежей, не используйте Redis для кэширования таких ответов.

Правильное поведение:

```text
Платёжный запрос → всегда идти в источник данных → не сохранять в Redis
```

---

## Аналогия

Кэш похож на шпаргалку рядом с учителем.

Если ученик часто спрашивает одно и то же, учитель быстро смотрит в шпаргалку. Но если вопрос про деньги и платежи, шпаргалку использовать нельзя: нужно проверять по оригиналу.

Ещё проще:

- обычный API без кэша — каждый раз заново собирать пазл;
- Redis — заранее собранная картинка, которая хранится 10 минут;
- платежи — документы, которые нельзя брать из «картинки на 10 минут»: они должны быть точными прямо сейчас.

---

## Что нужно помнить при разработке

1. Redis ускоряет чтение данных. Он особенно хорош для запросов, которые часто повторяются и не требуют идеальной свежести каждую миллисекунду.

2. Кэш не источник истины. Настоящие данные хранятся в базе или сервисе, а Redis только ускоряет доступ к ним.

3. TTL — 10 минут. Данные в кэше могут быть не самыми свежими, учитывайте это при проектировании UI и бизнес-логики.

4. Платежи не кэшируем. Никогда не добавляйте платёжные данные в Redis как кэш. Это запрещено.

5. Если данные критичны к свежести, подумайте дважды. Кэш уместен там, где допустима 10-минутная задержка в обновлении.

---

## Итог

Redis нужен, чтобы API работал быстрее: вместо 800 мс ответ занимает 40 мс.

Мы кэшируем данные на 10 минут, но никогда не кэшируем данные о платежах.

```text
Обычные быстрые данные → можно кэшировать
Платежи → никогда не кэшировать
```
