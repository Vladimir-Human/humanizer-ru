## Что такое кэш и зачем нам Redis

Кэш — это временное хранилище часто используемых данных. Он нужен, чтобы не запрашивать их каждый раз из «дорогих» мест: базы данных, внешних сервисов или тяжёлых вычислений. Если ответ на один и тот же вопрос можно быстро достать из памяти, незачем считать его заново.

## Зачем нам Redis

Redis — быстрое хранилище в памяти, которое мы используем как кэш. В нём на короткое время лежат готовые ответы API и промежуточные данные.

Разница по времени ответа такая:

- API без кэша: около 800 мс
- API с Redis: около 40 мс

Ответы получаются примерно в 20 раз быстрее. Интерфейс загружается почти мгновенно, а база и внешние сервисы получают меньше нагрузки.

## Как это выглядит на практике

Допустим, пользователь часто запрашивает список товаров, профиль категории или агрегированную информацию.

Без кэша каждый запрос идёт в базу:

```text
Запрос → проверка прав → запрос к базе → агрегация → ответ
```

С кэшем:

```text
Запрос → есть данные в Redis? → да → ответ
                         → нет → запрос к базе → сохранить в Redis → ответ
```

Если данные уже есть в Redis, мы не обращаемся к базе и не считаем всё повторно.

## Сколько хранится кэш

Кэш у нас живёт 10 минут. После записи в Redis данные хранятся там максимум столько, потом «протухают», и следующий запрос снова идёт в источник данных.

Например:

```text
00:00 — данные положили в Redis
00:05 — данные ещё валидны
00:10 — данные истекли, следующий запрос пойдёт в базу
```

Такой TTL (время жизни) выбирают как баланс между скоростью и актуальностью данных.

## Почему нельзя кэшировать всё подряд

Кэш полезен, но использовать его нужно аккуратно. Плохая практика:

- кэшировать данные, которые быстро меняются;
- показывать пользователям устаревшую информацию;
- кэшировать персональные данные, не понимая, кто и когда должен их видеть;
- кэшировать финансовые и платёжные операции.

Если данные изменили в базе, а кэш ещё живёт 10 минут, пользователь увидит старую информацию. Поэтому для части данных кэш не подходит или требует аккуратной инвалидации.

## Исключение: платежи

Данные о платежах мы никогда не кэшируем. Платёжная информация слишком чувствительная и должна быть актуальной на момент запроса. Кэш может показать устаревшее или неверное состояние платежа, а ошибки в платёжных данных могут дорого обойтись.

Если ваш код, API, дашборд или аналитика касаются платежей, не используйте Redis для кэширования таких ответов.

Правильное поведение:

```text
Платёжный запрос → всегда идти в источник данных → не сохранять в Redis
```

## Аналогия

Кэш похож на шпаргалку рядом с учителем. Если ученик часто спрашивает одно и то же, учитель быстро смотрит в шпаргалку. Но вопрос про деньги и платежи по шпаргалке не решают, его проверяют по оригиналу.

Ещё проще так:

- API без кэша: каждый раз заново собирать пазл;
- Redis: заранее собранная картинка, которая хранится 10 минут;
- платежи: документы, которые нельзя брать из «картинки на 10 минут», они должны быть точными прямо сейчас.

## Что помнить при разработке

1. Redis ускоряет чтение. Он особенно хорош для запросов, которые часто повторяются и не требуют идеальной свежести каждую миллисекунду.
2. Кэш не источник истины. Настоящие данные хранятся в базе или сервисе, а Redis только ускоряет доступ к ним.
3. Из-за TTL в 10 минут данные в кэше могут быть не самыми свежими. Учитывайте это при проектировании UI и бизнес-логики. Если данные критичны к свежести, подумайте дважды: кэш уместен там, где 10 минут задержки допустимы.
4. Платёжные данные в Redis не добавляем ни при каких условиях.

## Итог

Redis сокращает время ответа API с 800 до 40 мс. Данные в нём живут 10 минут, а платёжные данные мы не кэшируем.

```text
Обычные быстрые данные → можно кэшировать
Платежи → никогда не кэшировать
```
