## Кэш и Redis

Кэш — это временное хранилище часто запрашиваемых данных. Он нужен, чтобы не ходить каждый раз в «дорогие» места: базу данных, внешние сервисы, тяжёлые вычисления. Если ответ на один и тот же вопрос можно быстро достать из памяти, незачем считать его заново.

Redis — быстрое хранилище в памяти. Мы держим в нём готовые ответы API и промежуточные данные, но недолго. Разница заметна: API без кэша отвечает примерно за 800 мс, с Redis — за 40 мс, то есть в 20 раз быстрее. Пользователь видит интерфейс почти сразу, а база и внешние сервисы получают меньше нагрузки.

## Как это работает

Допустим, пользователь часто открывает список товаров, профиль категории или агрегированную сводку. Без кэша каждый такой запрос идёт в базу:

```text
Запрос → проверка прав → запрос к базе → агрегация → ответ
```

С кэшем путь короче:

```text
Запрос → есть данные в Redis? → да → ответ
                         → нет → запрос к базе → сохранить в Redis → ответ
```

Если данные нашлись в Redis, мы не обращаемся к базе и не повторяем вычисления.

## Сколько живёт кэш

У нас кэш живёт 10 минут. Записанные в Redis данные хранятся там не дольше, потом «протухают», и следующий запрос снова идёт в источник:

```text
00:00 — данные положили в Redis
00:05 — данные ещё валидны
00:10 — данные истекли, следующий запрос пойдёт в базу
```

TTL, то есть время жизни, выбирают как компромисс между скоростью и актуальностью.

## Что нельзя кэшировать без разбора

Кэшировать всё подряд не стоит. Под запретом или под особым вниманием:

- данные, которые быстро меняются;
- персональные данные, если не ясно, кто и когда должен их видеть;
- финансовые и платёжные операции.

Если данные в базе изменились, а кэш живёт ещё 10 минут, пользователь увидит старую информацию. Поэтому для части данных кэш не подходит или требует аккуратной инвалидации.

## Платежи

Данные о платежах мы не кэшируем никогда. Они слишком чувствительные, и актуальными должны быть на момент запроса. Из-за кэша пользователь может увидеть устаревшее или неверное состояние платежа, а ошибки в платёжных данных критичны.

Если ваш код, API, дашборд, аналитика или любой другой сценарий касается платежей, не используйте Redis для таких ответов:

```text
Платёжный запрос → всегда идти в источник данных → не сохранять в Redis
```

Проще всего представить шпаргалку рядом с учителем. Если ученик часто спрашивает одно и то же, учитель быстро заглядывает в неё. Но когда вопрос про деньги, шпаргалке верить нельзя, нужно сверяться с оригиналом.

## Что помнить при разработке

1. Redis ускоряет чтение. Он лучше всего подходит для запросов, которые часто повторяются и не требуют идеальной свежести каждую миллисекунду.
2. Кэш не источник истины. Настоящие данные лежат в базе или сервисе, а Redis только ускоряет доступ к ним.
3. Из-за TTL в 10 минут данные в кэше могут отставать. Учитывайте это при проектировании интерфейса и бизнес-логики. Если данные критичны к свежести, подумайте дважды: кэш уместен там, где задержка обновления в 10 минут допустима.
4. Платёжные данные в Redis не попадают, ни в каком виде.

```text
Обычные быстрые данные → можно кэшировать
Платежи → никогда не кэшировать
```
