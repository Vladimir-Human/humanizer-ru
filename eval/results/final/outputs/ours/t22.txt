## Что такое кэш и зачем нам Redis

Кэш — это временное хранилище часто используемых данных. Он нужен, чтобы не запрашивать их каждый раз из «дорогих» мест: базы данных, внешних сервисов или тяжёлых вычислений.

Если ответ на один и тот же вопрос можно быстро взять из памяти, незачем считать его заново.

---

## Зачем нам Redis

Redis — быстрый кэш и хранилище в памяти. Мы держим в нём готовые ответы API и промежуточные данные на короткое время.

Разница видна по цифрам:

- API без кэша: ~800 мс
- API с Redis: ~40 мс

Ответы приходят примерно в 20 раз быстрее. Пользователю интерфейс загружается почти мгновенно, а база данных и внешние сервисы получают меньше нагрузки.

---

## Как это выглядит на практике

Допустим, пользователь часто запрашивает список товаров, профиль категории или агрегированные данные.

Без кэша каждый запрос идёт в базу:

```text
Запрос → проверка прав → запрос к базе → агрегация → ответ
```

С кэшем:

```text
Запрос → есть данные в Redis? → да → ответ
                         → нет → запрос к базе → сохранить в Redis → ответ
```

Когда Redis отдаёт данные, мы не обращаемся к базе и не пересчитываем всё заново.

---

## Сколько хранится кэш

У нас кэш живёт 10 минут. После записи в Redis данные хранятся там максимум 10 минут, затем «протухают», и следующий запрос снова идёт в источник данных.

Например:

```text
00:00 — данные положили в Redis
00:05 — данные ещё валидны
00:10 — данные истекли, следующий запрос пойдёт в базу
```

TTL (время жизни) выбирают как баланс между скоростью и актуальностью данных.

---

## Что нельзя кэшировать

Кэшем нужно пользоваться аккуратно. Плохая практика:

- кэшировать данные, которые быстро меняются;
- показывать пользователям устаревшую информацию;
- кэшировать персональные данные, если непонятно, кто и когда должен их видеть;
- кэшировать финансовые и платёжные операции.

Если данные изменили в базе, а кэш ещё живёт 10 минут, пользователь может увидеть старую информацию. Поэтому для некоторых данных кэш не подходит или требует аккуратной инвалидации.

---

## Главное исключение: платежи

Данные о платежах мы никогда не кэшируем.

Это важное правило. Платёжная информация не должна храниться в кэше:

- она слишком чувствительная;
- она должна быть актуальной на момент запроса;
- кэш может показать устаревшее или неверное состояние платежа;
- ошибки в платёжных данных могут быть критичными.

Если ваш код, API, дашборд, аналитика или любой другой сценарий касается платежей, не используйте Redis для кэширования таких ответов.

Правильное поведение:

```text
Платёжный запрос → всегда идти в источник данных → не сохранять в Redis
```

---

## Аналогия

Кэш похож на шпаргалку рядом с учителем.

Если ученик часто спрашивает одно и то же, учитель быстро смотрит в шпаргалку. Но если вопрос про деньги и платежи, шпаргалка не годится: нужно проверять по оригиналу.

Ещё проще:

- API без кэша — каждый раз заново собирать пазл;
- Redis — заранее собранная картинка, которая хранится 10 минут;
- платежи — документы, которые нельзя брать из «картинки на 10 минут»: они должны быть точными прямо сейчас.

---

## Что нужно помнить при разработке

1. Redis ускоряет чтение данных. Он особенно хорош для запросов, которые часто повторяются и не требуют идеальной свежести каждую миллисекунду.

2. Кэш не является источником истины. Настоящие данные хранятся в базе или сервисе, а Redis только ускоряет доступ к ним.

3. TTL — 10 минут. Данные в кэше могут быть не самыми свежими, и это нужно учитывать при проектировании UI и бизнес-логики.

4. Платежи не кэшируем. Никогда не добавляйте платёжные данные в Redis. Это под запретом.

5. Если данные критичны к свежести, подумайте дважды. Кэш уместен там, где задержка обновления в 10 минут допустима.

---

## Итог

Redis нужен, чтобы API работал быстрее: вместо 800 мс ответ занимает 40 мс.

Мы кэшируем данные на 10 минут, но данные о платежах не кэшируем никогда.

```text
Обычные быстрые данные → можно кэшировать
Платежи → никогда не кэшировать
```
