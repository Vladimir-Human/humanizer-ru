# Как провести слепую оценку

Зачем это нужно: все остальные проверки репозитория контролируют внутреннюю
непротиворечивость. Они не отвечают на вопрос, становится ли текст лучше со скиллом,
чем без него. Этот прогон отвечает.

## Что считается автоматически, а что нет

| Метрика | Кто считает |
|---|---|
| Снятие маркеров | машина, через `check_markers.py --scan` |
| Дописанные факты | машина, через `check_examples.new_facts` |
| Ложные правки в человеческих текстах | машина |
| Изменение длины | машина |
| Читаемость | слепой судья |
| Потеря смысла | слепой судья |

Механическая часть работает без сети и без модели. Судья нужен только для
двух последних строк.

## Шаг 1. Собрать парный прогон

Один агент, одна модель, один промпт, одна температура. Различается ровно одно:
в ветке `with` скилл загружен, в ветке `without` — нет.

Структура каталога:

```
eval/runs/2026-07-26-baseline/
  manifest.json
  source/<id>.txt      исходный текст
  without/<id>.txt     результат без скилла
  with/<id>.txt        результат со скиллом
```

`manifest.json`:

```json
{
  "run": "2026-07-26-baseline",
  "model": "укажите модель и версию",
  "skill_version": "3.6.0",
  "prompt": "дословный промпт, одинаковый для обеих веток",
  "pairs": [
    {"id": "ai-01", "kind": "ai", "provenance": "captured-2026-07-25"},
    {"id": "hum-01", "kind": "human", "provenance": "research/validation/human"}
  ]
}
```

Поле `kind` важно. Записи с `human` — контрольная группа: их править было не нужно,
и любая правка в них считается ложным срабатыванием. Гарнесс требует хотя бы одной
AI-пару и не меньше трети человеческих контрольных пар. Без этого отчёт не создаётся.

Поле `provenance` заполняется честно. Если текст написан для проверки вручную,
так и пишется. Выдавать сочинённый образец за захваченный вывод модели нельзя:
весь смысл проекта в том, что его числа можно проверить.

## Шаг 2. Механические метрики

```bash
python3 eval/blind_eval.py --run eval/runs/2026-07-26-baseline
```

Отчёт ложится в `eval/results/`. При отсутствии файлов скрипт выходит с ошибкой,
а не с пустым отчётом. Это сделано намеренно.

## Шаг 3. Слепой судья

```bash
python3 eval/blind_eval.py --run eval/runs/2026-07-26-baseline --make-packet /tmp/packet
```

В `/tmp/packet/pairs/` лягут файлы вида `P001.md`: исходный текст и два варианта
без пометок. Порядок вариантов каждый раз выбирает криптографически стойкий
генератор: иначе судья выучит закономерность или восстановит её по публичному seed.

Ключ создаётся рядом с пакетом: для `/tmp/packet` это `/tmp/packet.key.json`.
Он намеренно лежит **вне** каталога пакета, чтобы его нельзя было случайно отдать
судье вместе с остальными файлами. Если судья — модель, ей передаются только
`INSTRUCTIONS.md`, `verdicts.template.json` и содержимое `pairs/`.

Заполненные вердикты возвращаются обратно:

```bash
python3 eval/blind_eval.py --run eval/runs/2026-07-26-baseline \
  --judgements /tmp/packet/verdicts.json \
  --key /tmp/packet.key.json
```

Скрипт сверит ключ с хешем прогона, потребует ровно один валидный вердикт на каждую
пару и только после этого расшифрует, какая ветка выиграла. Чужой или устаревший
ключ, пропущенная пара и неизвестное значение завершают прогон с ошибкой.

## Заморозка записи

Отчёт в `eval/results/` фиксирует механику той версией детекторов, которая
была на момент прогона. Если детектор фактов или маркеров потом менялся,
пересчёт чисел новой версией может отличаться от записанных — записанные
числа каноничны, а каталог прогона после генерации отчёта не правится:
`run_sha256` скрепляет прогон с ключом обезличивания, и любая правка
каталога ломает повторную расшифровку. Целостность всех `results`-файлов против
прогонов проверяет гейт `blind_eval.py --verify-results`.

## Чего делать нельзя

- Показывать судье ключ или названия веток.
- Редактировать файлы прогона после создания пакета: хеш перестанет совпадать.
- Оставлять пустыми `model`, `skill_version`, `prompt` или `provenance`.
- Прогонять ветки на разных моделях или с разными промптами.
- Выбирать тексты после того, как увидели результат. Корпус фиксируется до прогона.
- Публиковать только удачные метрики. Публикуется весь отчёт.

## Что считать успехом

Целевые значения до первого прогона не назначаются. Сначала базовый замер,
потом пороги от него. Назначить цель раньше замера — способ подогнать замер
под цель.

Единственное исключение — ложные правки в контрольной группе. Здесь цель известна
заранее и равна нулю.
